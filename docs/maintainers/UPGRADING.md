# 升级规则与执行流程（唯一维护源）

本文适用于任何AI或人工维护者。当前源码、分支及功能对照入口见[升级对照基线](UPGRADE_BASELINE.md)，开始工作前先走[接手流程](HANDOVER.md)。规则变动只改本文；Docs/CONVENTIONS及AGENTS保留引用，不另复制一套。

用户于2026-10-28确认：每次升级FlClash底座、SDK、原生插件或其他可能改变运行行为的依赖后，必须检查代码，审计**我们自己的品牌A/B客户端**升级前后的功能、行为与逻辑变化。该要求适用于任何AI或人工维护者，不能由上游团队维护、上游原版正常、合并无冲突、编译成功或已有测试通过替代。

### 先按本项目实际使用方式分类，再决定适配

每次升级前必须先依据真实生产调用关系，将上游变化逐项归入下表，再确定迁移范围；升级后按同一清单复核。**上游更新清单不是本项目的产品需求清单，不逐项照搬。** 同一功能可能同时含自有业务层与复用底座层，应按层、品牌及平台分别判定；无法确认用途的项目标为待确认，不能默认算“未使用”。

| 分类 | 核查重点 | 处理要求 |
| --- | --- | --- |
| 直接复用的底座能力 | 例如内核、Android VPN服务、系统代理、DNS、配置应用；核对真实入口、返回/失败语义、默认值和运行行为变化 | 适配确实影响本项目的变化，验证其符合品牌客户端已确认要求；不能把上游原版通过当作品牌适配已通过 |
| 我们自己的实现 | 例如品牌首页、出口IP检测、Xboard API竞速、加密订阅、更新流程、品牌图标；核对自有实现实际依赖的底座接口和状态 | 保留自有产品逻辑，只适配确实变化的底层契约；上游新增同名功能、界面或默认策略不自动替换自有方案。需要改变自有行为时说明理由并遵守既有用户决策/授权 |
| 未使用的上游功能 | 先证明没有品牌生产入口，再核对共用配置、数据库迁移、初始化、依赖和资源的间接影响 | 不为追随版本而新增入口或改变产品；存在间接影响时仍要适配并测试。“不接入”不等于擅自删除上游共享代码或拆散相互依赖的改动 |

例如，上游IP质量缓存不自动变成品牌出口IP的缓存策略；上游仪表盘简化或托盘图标更新，不自动改写品牌首页和图标。这些是分类方法的示例，不替代每次的源码核对。

1. **明确对照基线。** 记录升级前品牌客户端的实际提交/发布版本、升级后的提交及未提交差异，关联SDK、依赖与已知成品。上游新旧版本只作辅助对照，不得只比较原版FlClash，或把底座默认值当作品牌成品事实。基线/成品缺失标记待确认并说明影响。
2. **沿真实调用链核对。** 从品牌入口追踪到适配器、provider、SDK、原生插件和底座消费者，核对触发条件、默认值、返回值及失败语义、状态来源、异步时序、取消/旧结果隔离、生命周期和资源释放。不得只看接口名、注释、改动文件或mock；同时检查未修改但依赖旧语义的品牌代码，以及跨链路联动。
3. **覆盖完整产品和平台。** 至少核对启动/登录登出、Bootstrap/API竞速与故障恢复、加密订阅获取/校验/落地/内核应用、节点/模式/连接断开、IP与测速、代理/TUN/证书、前后台/网络切换、更新下载/安装交接、客服/教程、品牌身份/目录/单实例、配置/数据库/凭据迁移及权限/平台最低版本。品牌A/B与各支持平台分别核对；共用代码、平台专用路径和成品注入分别举证。不是每次都必须重跑全部测试，但不得无说明跳过检查范围。
4. **交付行为差异清单。** 每项记录上游变更、本项目使用分类及源码依据、升级前行为、升级后行为、源码位置/调用链、触发条件、影响品牌/平台、直接/间接影响、采用/保留自有/不接入的处理决定、是否符合用户已确认要求，以及证据和状态。明确区分预期变化、用户已接受变化、适配遗漏、旧版已有缺陷、已修复未出包、待验证；未发现变化也要注明核查范围，不以“应该一样”代替证据。
5. **验证实际边界。** 按风险补正负控，覆盖正式接线、真实默认实现、失败恢复、并发/迟到结果和升级旧数据；只证明mock会返回预设结果不足以验收。代码完成、测试通过、成品入包、符号上传、原生设备业务成功分别记录。没有平台/设备环境就列待验证及风险，不能把主题模拟或轻量检查说成原生验收。
6. **保留既有产品要求。** 发现未经用户接受的行为退化或关键逻辑变化，先报告原因、影响和处理建议；授权范围内修复并回归。涉及新接缝/依赖、产品目标或行为取舍时遵守既有提前告知/决策规则，不为“跟随上游”静默取消品牌能力，也不借审计擅改上游或用户已排除事项。
7. **完成门槛。** 升级实施后、交付前必须完成上述审计；后续修复还要复核相关联动。差异结论和验证缺口同步唯一负责的当前文档：升级规则在本文，对照地图在UPGRADE_BASELINE，调用链在Docs/ARCHITECTURE，行为契约在Docs/CONTRACTS，执行方法在Docs/DEVELOPMENT，证据/缺陷/待验收在Docs/STATUS。没有基于代码的差异清单、未解释的关键差异或缺少必要验证时，不得宣称“升级完成/全平台无问题”；应报告具体阶段和阻塞项。本约定不自动授权构建、提交、发布或线上操作。

## 行为对照表的维护口径

[UPGRADE_BASELINE](UPGRADE_BASELINE.md)是唯一行为映射表：F为稳定功能ID，P为平台入口，S只是既有接缝/复用锚点的索引组，U为未接入或间接影响，G为缺口索引。S索引不增加接缝数量；真实登记仍在PATCHES/FLCLASH_ANCHORS。

每项必须分开写：已确认用户要求或维护约束、固定原版提交的行为/入口、品牌当前调用链、两品牌及平台依赖、接缝、回归入口与必测失败分支、已知限制/待验收。没有上游等价业务就明确写无，不把通用HTTP/窗口/数据库等基础依赖包装成等价业务。

实现和要求冲突时登记缺陷，不能把旧实现自动升级成“必须保留”的产品规则。退役补丁先确认上游能满足同一行为契约，再通过对应正负控；本轮文档分类不授权改接口或退役接缝。依赖表须区分直接调用/输入与下游影响/联查，不能把同一事件的并列消费者写成串行依赖。测试入口必须反查实际框架、平台条件和被测逻辑，不能凭文件名认定覆盖；涉及真实Gradle/MSVC的Python驱动也属于原生环境检查。测试文件存在、Widget平台主题模拟、正式包成功及原生设备通过是不同证据。实际结果只维护STATUS，避免逐次回归数量复制到功能表。

当前先维护人工核实的行为映射；自动差异映射及新增测试工具不是本轮已交付能力。未知依赖和未覆盖平台必须显式标注及说明影响，不能靠“不在表里”免检。

## 每次升级的实际顺序

1. 先登记旧品牌客户端提交、旧上游提交、新上游实际tag/commit、SDK固定引用与未提交差异。用户未指定/未授权升级的版本不得自动作为目标。上游克隆只读，不安装其依赖或运行构建。
2. 用Git对象做上游差异，再用本项目接缝登记与对照表分配责任。示例中的变量必须先从本次真实登记取得，未填写时不要执行：

```bash
# 仅只读；先定义并核验 OLD_UPSTREAM 和 NEW_UPSTREAM 为实际提交。
: "${OLD_UPSTREAM:?缺旧上游提交}" "${NEW_UPSTREAM:?缺新上游提交}"
git cat-file -e "${OLD_UPSTREAM}^{commit}"
git cat-file -e "${NEW_UPSTREAM}^{commit}"
git diff --stat "$OLD_UPSTREAM" "$NEW_UPSTREAM"
git diff --name-status "$OLD_UPSTREAM" "$NEW_UPSTREAM"
```

3. 逐行检查[当前对照表](UPGRADE_BASELINE.md)：上游改动→实际消费者→品牌规则→平台入口。不能只看Git报告冲突的文件。每项在本次记录写明采用、保留自有、不接入或待确认。
4. 新增、调整、移除接缝先告知具体文件、用途、必要性、平台及类型；新接缝/依赖按当前授权取得用户决策，已授权不重复询问。PATCHES/FLCLASH_ANCHORS仍是机器登记唯一源，不把功能表当白名单。
5. 小批适配后先检查源码，再执行适当轻量回归和已授权主机预检。macOS/iOS无设备或无Runner结果时保留缺口，不拿Linux主题模拟代替原生验证。
6. 提交前分别审阅客户端/SDK/Docs，先提交被固定引用的仓库，再更新客户端CI引用。提交不等于构建授权；构建不等于发布/合并main授权。
7. 每次失败更新[构建失败经验](../build-failures/README.md)，按底座版本归档实际修复及正负控。构建后的APK/EXE/AppImage/DMG、匹配符号和设备行为是独立验收。
