# 升级规则与执行流程（唯一维护源）

本文适用于任何AI或人工维护者。当前源码、分支及功能对照入口见[升级对照基线](UPGRADE_BASELINE.md)，开始工作前先走[接手流程](HANDOVER.md)。升级分类和执行顺序只改本文；编号/行为映射归UPGRADE_BASELINE，具体命令归WORKFLOWS，两级验收归ACCEPTANCE，材料归档归MATERIALS。其他入口引用对应维护源。

用户于2026-10-28确认：每次升级FlClash底座、SDK、原生插件或其他可能改变运行行为的依赖后，必须检查代码，审计**我们自己的品牌A/B客户端**升级前后的功能、行为与逻辑变化。该要求适用于任何AI或人工维护者，不能由上游团队维护、上游原版正常、合并无冲突、编译成功或已有测试通过替代。

### 先按本项目实际使用方式分类，再决定适配

每次升级前必须先依据真实生产调用关系，将上游变化逐项归入下表，再确定迁移范围；升级后按同一清单复核。**上游更新清单不是本项目的产品需求清单，不逐项照搬。** 同一功能可能同时含自有业务层与复用底座层，应按层、品牌及平台分别判定；无法确认用途的项目标为待确认，不能默认算“未使用”。

| 分类 | 核查重点 | 处理要求 |
| --- | --- | --- |
| 直接复用的底座能力 | 例如内核、VPN/原生磁贴与快捷操作、系统代理/DNS、配置应用、可达底座子页和托盘菜单；分开核对品牌输入/身份接缝、底座执行、原生完成及外层错误处理。执行层复用不代表输入层没有接缝 | 适配确实影响本项目的变化，验证其符合品牌客户端已确认要求；不能把上游原版通过当作品牌适配已通过 |
| 我们自己的实现 | 例如品牌首页、出口IP检测、Xboard API竞速、加密订阅、更新流程、品牌图标；核对自有实现实际依赖的底座接口、状态与资源路径；按平台/布局及正式打包入口检查最终资源覆盖，不能由源码图片存在推断入包正确 | 保留自有产品逻辑，只适配确实变化的底层契约；上游新增同名功能、界面或默认策略不自动替换自有方案。需要改变自有行为时说明理由并遵守既有用户决策/授权 |
| 未使用的上游功能 | 生产入口范围包括品牌外壳可达的原版子页及其二级/更深页面、复用托盘/快捷操作、启动和后台动作；再查共用配置、数据库迁移、初始化、依赖与资源。不能只查lib/xboard直接引用 | 不为追随版本而新增入口或改变产品；存在间接影响时仍要适配并测试。“不接入”不等于擅自删除上游共享代码或拆散相互依赖的改动 |

例如，上游IP质量缓存不自动变成品牌出口IP的缓存策略；上游仪表盘简化不自动替换品牌首页；不自动采用上游图标，但必须核对品牌资源是否覆盖上游新增或变更路径。品牌支付业务保持自有逻辑，但二维码渲染已直接复用原版QrCodeView，后续该组件变化按直接复用核对。这些是分类方法的示例，不替代每次的源码核对。

### 每项功能的分层检查

按F功能组织，逐层记录：品牌输入/身份/默认值 → 底座动作 → 原生或数据库完成 → UI显示及失败恢复。至少覆盖正常、失败、取消/取代、暂停、启动守卫降级、旧数据和初始化路径；SAFE_MODE编译开关另行核对，当前正式入口未启用；返回true、收到应答、写入完成和内核生效分别解释。对共享配置同时比较新装默认、旧配置迁移、已有显式值和备份恢复，不能把默认值当所有用户的有效值。

启动守卫须区分Android的skipAutoSetup与clearProfile（清空当前选中ID，不删除Profile数据），不能用SAFE_MODE代称。

原生磁贴、Android启动器/外部应用快捷动作、受签名权限保护的广播、桌面托盘与全局快捷键、autoRun分别沿实际调用追踪；Android共用启动路径按host.tile()是否可用区分Dart转交与原生保存状态恢复，并单独核对停止路径，不能统称为首页按钮或普通桌面快捷方式。它们是否需要额外品牌门禁取决于已确认要求；发现未明确约束先登记，不因升级审查擅自增加限制。TV等保留入口与正式支持承诺、品牌资源完成度分开判断。

## 对照表维护

编号和字段定义只维护在[UPGRADE_BASELINE](UPGRADE_BASELINE.md#分类与证据用法)。沿真实调用链区分用户决定、维护约束、实现、限制；不把旧缺陷升级成产品要求，不以测试存在代替覆盖。用户要求附决定出处/记录日期；无法查明日期就标待确认，不编造。共享依赖变化即使没有文件重叠，也必须追踪消费者。

## 每次升级的实际顺序

1. 先登记旧品牌客户端提交、旧上游提交、新上游实际tag/commit、SDK固定引用与未提交差异。用户未指定/未授权升级的版本不得自动作为目标。上游克隆只读，不安装其依赖或运行构建。
2. 用Git对象保存上游改动清单、与旧品牌差异的重叠路径，以及品牌包/相对导入和export/part闭包报告；结合PATCHES、锚点核对底座反向调用品牌的接缝，并联查原生、资源和构建入口。简单直接导入筛选只作快速预览；按[WORKFLOWS的只读差异命令](WORKFLOWS.md#升级差异采集)执行。记录固定输入与dirty范围；筛选只是候选定位，不能自动认定不命中的文件无影响。

3. 按[MATERIALS的升级归档清单](MATERIALS.md#升级证据归档)保存输入和输出，再逐行检查[当前对照表](UPGRADE_BASELINE.md)：上游改动→实际消费者→品牌规则→平台入口。不能只看Git报告冲突的文件。每项在本次记录写明采用、保留自有、不接入或待确认。
4. 新增、调整、移除接缝先告知具体文件、用途、必要性、平台及类型；新接缝/依赖按当前授权取得用户决策，已授权不重复询问。PATCHES/FLCLASH_ANCHORS仍是机器登记唯一源，不把功能表当白名单。
5. 小批适配后先检查源码，再执行适当轻量回归和已授权主机预检。macOS/iOS无设备或无Runner结果时保留缺口，不拿Linux主题模拟代替原生验证。
6. 按[ACCEPTANCE两级门槛](ACCEPTANCE.md#升级合并与发布门槛)分别判断可合并、可发布；取得对应授权后按[WORKFLOWS合并步骤](WORKFLOWS.md#合并升级成果到-main)操作。合并、构建、草稿上传、公开发布是不同动作，不相互推导授权。
7. 每次失败更新[构建失败经验](../build-failures/README.md)，按底座版本归档实际修复及正负控。构建后的APK/EXE/AppImage/DMG、匹配符号和设备行为是独立验收。
