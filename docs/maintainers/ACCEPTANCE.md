# 任务验收标准

本页是客户端项目的统一验收入口，适用于品牌A/B、SDK及相关文档和运维任务。权限与产品规则由[CONVENTIONS](https://github.com/wvjh3z/proxy-suite-docs/blob/main/CONVENTIONS.md)维护；执行方法见[WORKFLOWS](WORKFLOWS.md)，材料归属见[MATERIALS](MATERIALS.md)。本页定义通过条件，不自动授权提交、构建、部署、联网测试或生产变更。

## 通用通过条件

任务开始时确定实际目标、允许动作、涉及品牌/平台及本轮要证明的层级。结束时必须能够从项目资料找到以下信息，无需询问原维护者或读取聊天：

1. **目标明确**：仓库、分支、源码提交及必要未提交差异；构建任务还包含产品版本/构建号、平台/架构、实际运行ID，不能把Actions序号当构建号。
2. **要求明确**：用户已确认的行为、边界与取舍有唯一维护入口；关键歧义已解决，未知写明影响和取得证据的方法。常规实现选择在既有授权内执行。
3. **证据对应**：实际命令、环境、结果和产物能对应同一候选源码；记录跳过、失败和未验证内容。测试替身、原生入口、正式包、设备业务结果不能互相替代。
4. **结果可判断**：结论有生产调用或实际观测支持；发现冲突必须解决或明确保留，不能静默选取有利结果。文档变更不关闭业务缺陷。
5. **交付可取得**：可复用实现和必要证据按用途归档；接手者具备或能明确申请资料访问条件。只有本机忽略文件或聊天附件的结论不算正式交接。

## 按任务选择验收

每行只验本次任务范围。未涉及的平台可说明“不适用”及依据；共用代码影响两个品牌时须说明共用证据和品牌专属输入的覆盖，不能以A通过推定B全部通过。

| 任务 | 必需证据与通过条件 | 不通过或只能部分完成 | 详细入口 |
| --- | --- | --- | --- |
| 文档接手与整理 | 从当前入口找到目标、权限、环境、真实命令、成功条件、失败恢复及资料位置；在授权范围内走通代表性接手路径，链接/归属/重复检查通过 | 需翻聊天、依赖某AI记忆或旧Docs；只有链接有效但无法执行；新机器关键输入无入口 | [HANDOVER](HANDOVER.md#4-用证据验收文档是否可接手) |
| 代码审计与问题定位 | 追踪真实入口和消费者；区分现象、源码事实、根因推断及复现证据，覆盖相关品牌/平台 | 只搜索名字、引用注释、把超时当根因；未复现却称已证根因 | [功能基线](UPGRADE_BASELINE.md)、Docs/ARCHITECTURE |
| 缺陷修复 | 说明触发条件和修改后的行为；按风险覆盖正常、错误/取消、并发/迟到结果及恢复；回归确实命中缺陷，保持原安全边界 | 仅mock预设通过、放宽断言绕开错误、正式入口未覆盖；没有环境则保留原生/设备待验 | [按改动选测试](https://github.com/wvjh3z/proxy-suite-docs/blob/main/DEVELOPMENT.md#按改动选测试和验收) |
| 底座/依赖升级 | 按三原则逐项对照旧品牌行为、新实现、间接影响、接缝及迁移；记录已接受差异和验证缺口 | 只对照上游更新说明、仅解决合并冲突或编译通过 | [UPGRADING](UPGRADING.md) |
| 构建脚本与预检 | 同源码、正式命令及关键环境；涵盖受影响的干净Runner/空缓存/编码/路径/进程失败场景，正负控有效 | 本机暖缓存成功推定CI成功；负控因缺工具失败；诊断掩盖主退出码 | [失败经验](../build-failures/README.md)、[构建机手册](https://github.com/wvjh3z/proxy-suite-docs/blob/main/environments/BUILD_HOSTS.md) |
| 正式包与草稿发布 | 逐目标job、实际文件名/版本/签名/架构、品牌fallback和关键资源、匹配符号及服务端逐项处理、草稿资产归属分别核对 | 只有总状态绿、混入旧草稿资产、符号命令成功无匹配证据；设备未验则只能称制包/发布层通过 | [构建流程](WORKFLOWS.md#github正式构建需单独授权)、Docs/DEVELOPMENT |
| 安装/更新与设备业务 | 使用可追溯的实际包；按受影响场景核对旧版覆盖、全新安装、数据/身份隔离、失败恢复及启动登录/订阅/连接链路 | Runner制包成功替代设备安装；进程启动替代业务恢复；停机或数据风险未说明 | [设备操作表](https://github.com/wvjh3z/proxy-suite-docs/blob/main/runbooks/DEVICE_ACCEPTANCE.md#设备业务验收执行表)、[平台基线](UPGRADE_BASELINE.md#各平台安装退出边界)、Docs/STATUS对应缺陷关闭条件 |
| 运维查询/变更/恢复 | 真实对象、当前授权、采集时间、动作前后观测；变更有适用的恢复条件与材料；查询不扩大为配置修改 | 命令退出0即称恢复；仅看旧快照；原始数据丢失或不能核对采集是否完整 | [ACCESS](ACCESS.md)、构建机手册及相关专项步骤 |
| 提交交付 | 审阅三仓范围、敏感/生成文件与既有差异；先提交依赖仓再同步真实SDK/Docs引用，核对远端可取得 | 仅本机未提交即称已交付、pin指向不存在提交、把提交授权扩大为构建/main合并 | [跨仓交付](WORKFLOWS.md#提交与跨仓固定引用) |

客户端取消安装包下载SHA256校验的既有决定不变；安装包记录使用品牌、产品版本、构建号、平台/ABI、文件名和构建run，不要求手工维护安装包SHA256；原签名与匹配符号验收继续保留。凭据和生产原始数据的保护也不改变现有业务TLS/Sentry采集策略。

## 文档本身如何验收

[接手演练](HANDOVER.md#4-用证据验收文档是否可接手)须在当前授权内实际走查。检查命令语法只证明可解析，链接检查只证明目标可定位；没有凭据、主机或设备时明确受阻层级，不执行未经授权的操作来补齐表格。

所有影响维护判断的信息应有入口：实际身份与版本、配置维护源、权限和凭据取得方式、执行环境、工具约束、用户决定、缺陷/待验、已验证边界、失败处理及恢复材料。凭据值不写入文档。不同AI可用Git、Shell、Python、HTTP/OpenSSH等通用方法完成同一授权步骤；skill可辅助，不得是唯一知识源。

先更新已有负责章节；只在职责确实独立时拆分文档并留下导航。当前结论与历史过程分开，详细日志/截图不堆进规则正文。出现同一事实两处维护、过大的阶段流水账或已失效入口，应合并、归档或修正负责文档，不能只再加一段说明。

功能变更的文档通过条件：按[文档闭环](WORKFLOWS.md#功能变更的文档闭环)完成影响定位、旧说法处置和语义核对；当前操作入口无未解释冲突，必要回归/原型与源码一致，并列明同步范围及未验层级。只有链接/格式检查通过、只更新STATUS或只新增一份说明，均不足以证明完成。历史证据保留当时事实，未验不写成已通过。

## 完成状态与收尾

使用明确层级：**本轮范围通过 / 部分完成 / 阻塞 / 不适用**，附证据和原因。“源码修复、原生待验”“构建通过、设备待验”均是有限结论；已授权且可完成的必要工作不能因写了“待验”就提前结束。用户禁止构建时完成允许的检查，设备层保持待验，不把它记为失败或擅自构建。

收尾检查：要求与实现一致；所有相关品牌/平台有结论或合理缺口；材料已归位且可取得；链接和重复内容已检查；无凭据、临时输出或其他任务差异误入提交；原有任务材料未被清理。结果写入唯一负责的STATUS/失败记录/证据索引，不新增一份同义“完成报告”。

证据记录最低字段（字段模板，不是已执行结果）：任务与范围、日期/时区、源码/dirty说明、品牌/平台/包或运行ID、环境与命令、结果及跳过、证据位置和访问条件、未确认影响/下一步、必要恢复入口。只保留本任务适用字段；大型或敏感文件登记清单与摘要，不贴原文。

## 升级合并与发布门槛

两个门槛分别判断，不能由合并成功、正式job绿色或草稿存在推导可公开发布；既往已合并批次仍保留真实缺口，不追溯伪造通过记录。

| 门槛 | 必须具备 | 仍可保留的明确边界 |
| --- | --- | --- |
| 可合并main | 用户合并授权；固定上下游与品牌基线；上游变化→F映射及行为差异记录；候选或未分类项须完成判断，无法完成的风险须由用户明确接受，不能仅因文件存在判定审查完成；关键行为/数据/权限歧义已解决或由用户明确接受；相关回归与负控，原生缺环境的风险已明示；三仓引用可取得、编号不回退、敏感文件/旧差异保护；按WORKFLOWS同步入口和AGENTS | 可保留已接受的设备待验或暂停事项，但不得将其写成已验证；编号全局预留和CI验签自动化若未实现须留REL待办，不能因合并关闭 |
| 可发布给用户 | 另有发布授权；每品牌/架构的实际包身份、ABI、资源/fallback、按平台政策的签名身份与可安装性（Android必须匹配原品牌证书）；对应符号逐项处理及实际覆盖限制；受影响设备业务/升级恢复证明或用户明确接受的未验范围；必要旧包/符号可恢复、证据未过期并完成归档；同品牌发布编号无跨分支重复 | 草稿制包成功仅算制包层。缺少该平台要求的签名、匹配符号、恢复材料或未解释的关键差异不能静默放行；已接受限制须对使用范围明确说明 |

发布时的具体风险门禁：

Android原证书比对是当前明确要求；Windows/macOS签名、公证及Linux包签名分别按该批次已确认发布政策核对。没有采用签名的平台须记录实际状态及用户接受范围，不从Android要求推导“所有平台已有原签名”，也不因任务成功宣称已签名/公证。

- Android必须对**最终APK**验签并比对本品牌原证书；GitHub正式链当前未自动做这项独立比对（REL-02），不能把签名配置或打包成功当验签。独立操作见[最终APK原证书验收](https://github.com/wvjh3z/proxy-suite-docs/blob/main/runbooks/DEVICE_ACCEPTANCE.md#最终apk原证书独立验收)，自动化另行实施。
- Actions证据以实际到期时间为准，按MATERIALS转存；过期后缺失就保持缺口，不能用workflow声明的保留天数代替证据。
- 同品牌草稿覆盖前保留上一批可恢复材料；每个包、符号、清单必须属于同一批次。
- 目标是同品牌跨发布分支编号唯一且不回退；当前分支内回写不提供全局预留（REL-01）。自动化完成前只能在授权发布时按[编号核对步骤](WORKFLOWS.md#发布编号跨分支核对)核对所有已知分支/发布记录并串行分配，未知历史则标阻塞；不能宣称此人工检查解决了任意并发客户端的竞态。

REL-01/REL-02仍为未实现的自动化，不把文档门槛当实现。

**已明确授权的同号替换例外**：仅限用户明确指定的批次，不能推广为默认允许重用编号。品牌B VDS build36替换GitHub #148的范围与证据见[批次记录](https://github.com/wvjh3z/proxy-suite-docs/blob/main/evidence/brand-b-build36-vds-icon-replacement/README.md)。两个包的release均为brand_b@0.0.1+36，无法仅按release区分来源；应保留各自来源/批次、原签名验收和匹配符号，事件是否可由debug ID等进一步定位须实际核对，不直接断言符号混乱。同号不会触发更高版本提示，覆盖安装、缓存和设备行为需验收或记录用户接受范围；未增加全局编号或CI验签。
